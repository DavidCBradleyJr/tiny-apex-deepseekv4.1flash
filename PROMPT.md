<!-- Original task brief for this repository, reproduced verbatim. -->

Build **Tiny Apex**, a finished, polished, playable one-button arcade racing game in this repository. Implement the game and verify it with the tools available to you. Do not stop at a plan, mockup, screenshot or code pasted into chat.

### Outcome and priorities

The game should feel like a tiny premium arcade toy: immediately understandable, satisfying to control, visually distinctive, and inviting to replay. Prioritize, in order: working gameplay and reliable controls; clear visual feedback; cohesive art direction; small finishing details. Resolve ordinary design decisions yourself. Complete this as one autonomous task, including your own testing and fixes, without requesting a follow-up prompt. There is no artificial time target. Respect the environment's existing usage limits; do not change providers, billing or permissions.

Start from the supplied isolated project directory, even if it is empty. Setting up the project is part of this task. Inspect the files, project instructions, available terminal/browser tools, Node.js and npm versions, and any package manifest or lockfile before changing anything. Do not overwrite unrelated files. Use vanilla TypeScript, Vite and Three.js directly, with HTML/CSS for the interface; no UI framework, physics engine or external modeling tool is necessary.

If a shared setup manifest or lockfile was supplied, preserve its exact package versions and package manager; install from that lockfile with its reproducible install command (npm ci for package-lock.json). If none exists, create a minimal package.json, index.html, TypeScript configuration and src directory yourself. Install three as the runtime dependency and vite, typescript and compatible @types/three as development dependencies from the official npm registry. Use exact direct-dependency versions and retain the generated lockfile. Check compatibility instead of inventing version numbers. Do not copy a starter from another model's output. Keep the dependency set small and purposeful.

Check the selected Vite release's Node engine requirement before installing. The official guide checked for this brief lists Node 20.19+ or 22.12+ as minimum baselines; prefer a supported compatible LTS release and obey the actual package's engine constraints. If Node/npm is missing or incompatible, set it up only through an already permitted, user-local official Node.js distribution or existing approved version manager. Do not use sudo, change system-wide software, weaken security, obtain credentials, add paid services or expand permissions. If the required runtime or installation network access is unavailable within existing permissions, report the exact blocker rather than pretending setup succeeded or switching stacks.

Create working npm scripts: dev for the local Vite server; typecheck for TypeScript without emission; build for typecheck followed by the production Vite build; preview for serving dist locally; and test for focused noninteractive simulation tests. Use the built-in Node test runner with a small test-compilation step when suitable, or add only a minimal reputable project-local test runner if necessary. Do not create a fake test script that always succeeds. Verify installation and the minimal build before implementing the game. Bind servers locally; use a different host only if the supplied environment explicitly requires and permits it.

Use existing browser/screenshot tools when available. If browser automation is absent but local automation is permitted, you may install a compatible project-local Playwright release and its required browser through its official tooling, within the same workspace or an already allowed user cache. Do not install OS packages, browser extensions, MCP servers or new account integrations. If the browser cannot run without those changes, continue with terminal tests and report browser-dependent checks as unverified. Having a package installed does not prove that browser control, screenshots or WebGL work; check them. Do not claim access to tools that are not actually available.

Package and official development-tool downloads are allowed during setup; that exception does not allow downloaded game assets. Once setup is complete, keep dependencies fixed unless a necessary compatibility repair is required; document any repair. Keep code understandable with a small number of purposeful modules.

Everything visible must be authored in code: car, wheels, road, curbs, terrain, rocks, cactus silhouettes, signs, decorations and effects. Use Three.js primitives, shapes/extrusions or custom BufferGeometry. You may create textures using Canvas, simple procedural shaders, or inline SVG you write yourself. Use system fonts. Do not use downloaded models, images, textures, fonts, icon packs, stock assets, asset-generation services, external modeling tools, remote APIs or runtime CDNs. Do not use Blender, Tripo, GLTF/GLB/OBJ assets, or another model/agent. The result must run locally without external network requests after development dependencies and any permitted test browser are installed. Do not deploy or publish it.

### Art direction

Create a sunlit miniature desert circuit on a sculpted raised base, presented from an elevated three-quarter view. Aim for a coherent low-poly, toy-like aesthetic: warm sand and terracotta, dark asphalt, cream road markings, restrained teal accents, and a bright contrasting race car. Build a recognizable car with a shaped body, cabin, four wheels and a few deliberate details rather than an undecorated box. Use warm directional lighting, soft-looking contact shadows and enough material variation to make the scene feel dimensional.

Give the circuit a clear start/finish line, readable boundaries, alternating curb sections and a few distinctive landmarks. Compose scenery around the racing line without hiding the car or the next corner. Choose the exact composition, decorative forms and interface styling yourself. Prefer a few well-designed objects over clutter. Keep the whole circuit readable while playing, with the car clearly identifiable at phone size. An orthographic or restrained-perspective camera is appropriate. Fit the view to each viewport rather than stretching the scene.

Add purposeful motion: rotating wheels, a small cosmetic yaw/lean while turning, and restrained, short-lived tire marks or dust. Make steering activation, checkpoint progress and a crash visibly distinct. Cosmetic drift must not change the collision shape or steering rules. Avoid strobing, intense camera shake, expensive postprocessing and audio. Respect reduced-motion preferences for decorative animation.

### Fixed gameplay contract

This is arcade steering with drift-like presentation, not a tire-physics simulation. The car moves on a flat XZ plane. Hold Space or the large on-screen steering control to turn clockwise as viewed from above; release to drive straight. Forward speed is constant while racing. Do not add automatic steering, acceleration, braking, random obstacles, opponents, upgrades or difficulty scaling.

Use a stadium-shaped circuit: two straight centerline segments of 14 world units joined by two semicircles of radius 8. The road's full drivable width is 4, centered on that path. Car speed is 8 world units per second; held steering changes heading by 1 radian per second clockwise. This makes its turning radius match the track. You can rotate and position the circuit freely in the world, but preserve these dimensions and mechanics. Spawn on the centerline at the beginning of a straight, pointing toward its far end. A new run always starts in the same place and orientation.

Use a circular collision footprint of radius 0.65 centered on the car, and fit the visible car reasonably within that footprint. Crash when the footprint extends outside the road, considering both the inner and outer edges. Road graphics, collision and checkpoints must use the same track definition. Decorative scenery must not create invisible collisions. Never turning must eventually crash; holding forever must also eventually crash. A correctly timed straight/turn sequence must be capable of completing laps.

Place eight checkpoints evenly by distance around the centerline, with the eighth at the start/finish line. Award one point only for passing the next checkpoint in order in the forward direction while on the road. Use checkpoint gates spanning the road and crossing detection, so a valid pass is not missed between simulation steps. After checkpoint eight, increment completed laps and repeat the sequence. Merely surviving, revisiting old checkpoints, or crossing the finish early must not score. Highlight the next checkpoint without obscuring the road. Show checkpoint points and completed laps separately. Keep the rules deterministic; no gameplay randomness.

### States, input and layout

Provide ready, racing, paused and crashed states. The initial ready screen must show the actual attractive 3D scene, concise instructions and an obvious Start button. The car stays still until Start. Keep "Hold to turn. Release to go straight." visible during play. Show points, laps, current state and a clearly labeled steering control. A crash stops movement and scoring, makes the failure location clear, and shows a prominent Restart action with the run result. Restart resets the car, points, laps, checkpoint progress, held input, effects and simulation clock.

Space must not scroll the page during gameplay. Handle keyup, pointerup, pointercancel and lost pointer capture. Releasing a touch after dragging off the button must release steering. Keep pointer and keyboard input consistent, including when both were held. Clear all input and pause when the window loses focus or the page becomes hidden. Returning must show Resume, never silently resume or fast-forward. Reset timing on resume. UI buttons must not accidentally leave steering active.

Support 1440×900 desktop and 390×844 portrait viewports, plus resizing between them without changing world geometry or game progress. At each size the circuit, car, HUD and essential controls must be visible without horizontal scrolling, overlap or clipped labels. The touch steering target must be at least 64×64 CSS pixels. Use real labeled buttons, keyboard-operable menus, visible focus, readable contrast and text as well as color to communicate state.

### Technical reliability

Separate simulation state from rendering. Use one animation loop and a fixed simulation timestep with an accumulator, independent of display frame rate. Use a reasonable fixed step such as 1/120 second; bound catch-up after a long interruption and reset the clock after pause/resume so the car does not leap forward. Avoid duplicate loops/listeners on restart. Update renderer dimensions and camera projection when the canvas size changes. Cap rendering resolution appropriately for high-DPI phones. Share geometries/materials where practical, keep shadow-casting lights few, and bound transient effects so particles and skid marks cannot grow forever.

Aim for smooth play on a typical modern laptop and phone, but do not claim a frame rate you did not measure. Handle renderer initialization failure with a readable message instead of a blank page. Do not mask game errors with fake success states.

Inspect console errors and screenshots if these tools are available. Fix problems you discover within this same task, then rerun affected checks. Passing a build alone is not evidence that gameplay works. Do not weaken rules or tests to obtain a pass.

Your final response should briefly state what you built, commands/tests actually run and their observed results, and any remaining defects or unverified behavior. Report measured total wall-clock time from task start, including tool setup, downloads, implementation and testing; give setup time separately if measured.
